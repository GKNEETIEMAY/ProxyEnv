## 2. 从已验证握手取得主机身份

**建议保留 Windows OpenSSH，使用单一已信任主机密钥加成功握手来取得可证明的身份。** 首版范围是可独立确认的直接测试主机及单一普通主机公钥。公钥完整值来自维护者已验证的主机记录或独立的管理通道，并与现有 SSH 信任资料、端点、端口和撤销状态核对。只接受现有信任约束与独立审查的交集。测试环境优先使用受双方策略允许的 `ssh-ed25519`。共用密钥的克隆需要独立主机密钥才能入册。
[OpenSSH 主机核验](https://man.openbsd.org/ssh#VERIFYING_HOST_KEYS) · [OpenSSH 主机密钥算法](https://man.openbsd.org/ssh_config#HostKeyAlgorithms) · [撤销主机密钥](https://man.openbsd.org/ssh_config#RevokedHostKeys)

1. 从经批准的标准 SSH 公钥二进制 blob 计算 SHA-256，比较 32 字节值。不要散列 Base64 文本、注释或本机显示的指纹字符串。冻结后的专用 `known_hosts` 只含该目标的唯一许可公钥和适用撤销约束。根据受控 `HostKeyAlias` 或实际主机与 SSH 端口建立正确匹配，拒绝多个可能信任入口。
2. 使用该专用信任集合和 `StrictHostKeyChecking=yes` 开启一次无转发的认证 SSH 探测。固定远端 Windows 探测命令必须回送当次随机值，严格校验回执并正常退出，再复核绑定和连接代次。OpenSSH 负责校验对端用主机私钥对本次密钥交换数据的签名。唯一可信公钥加这次认证成功，才足以签发绑定该密钥的 `VerifiedHostIdentity`。记录证据来源、启动快照摘要、代次和时间，日志仅保存可诊断的分类。
3. 后续转发进程和监听复核分别进行新的握手，使用同一只读配置、目的地和唯一公钥。独立的探测成功不会把新进程自动标为可信。只有新进程仍按同一信任约束运行且经过其转发的回执抵达本机，才接受当前通道证据。任何密钥轮换都停止旧计划，重新办理既有主机信任与策略审查。
4. 不使用 `ssh-keyscan`、未完成握手的 PTY 提示、调试文本、远端自行报告的指纹或 `ssh -G` 结果签发身份。`KnownHostsCommand` 也可能在算法选择时调用，不能作为握手完成信号。若现有 CA、别名、撤销或复杂信任策略无法无损冻结，首版拒绝该目标。
   [OpenSSH 密钥交换验签实现](https://github.com/openssh/openssh-portable/blob/V_9_5_P1/kexgen.c#L190-L207) · [StrictHostKeyChecking](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) · [KnownHostsCommand](https://man.openbsd.org/ssh_config#KnownHostsCommand)

上述证明依赖 OpenSSH 的退出状态、真实回执和唯一许可公钥。Windows OpenSSH 的实际构建、认证方式、别名与撤销兼容性仍待实机完成。此前 M2 的回执不应倒签成已验证的主机身份。

## 3. 服务端策略的独立核验、入册与撤销

| 阶段 | 必须记录或验证 |
| --- | --- |
| 独立核验 | 由有权限的主机维护者通过独立管理通道确认实际运行的 Windows `sshd.exe` 版本、服务实例及启动配置。读取有效 `GatewayPorts=no`、当前账号允许的远端转发、`DisableForwarding` 与 `PermitListen`，并核对适用的 `Match` 条件和所用认证密钥的转发限制。使用该版本支持的有效配置检查，例如在确认可用时用 `sshd -T -C` 检查实际连接元组，再用部署记录关联正在运行的服务。普通 SSH 用户报告或某份配置文件的文本不足以完成此核验。 |
| 入册 | 由另一维护者审查工单与主机公钥。记录 ID、修订、服务实例或配置代号、服务端版本、主机公钥 SHA-256、主机与 SSH 端口、账号、适用来源及 `Match` 范围、批准远端端口、起始时间、到期时间及证据引用。审查记录持有 `GatewayPorts=no`，`clientspecified`、`yes` 和未知均拒绝。默认代码清单继续为空，另行审查才可登记测试主机。 |
| 生效 | 建议为受管理试点增加维护者签发的短期许可和撤销状态。签名校验公钥由维护者独立配置。许可绑定既有清单记录及修订、服务代号、端点、账号与端口范围。核对签名、明确用途、有效区间、最新撤销状态和已见最大修订，结合单调时钟限制会话有效期，拒绝回拨或失效状态。该流程待维护者评审，当前没有运行时签发、导入或查询接口。 |
| 失效与撤销 | 换主机密钥、重启或更换服务实例、修改授权范围、失去策略确认、过期或撤销均停止建立新转发。任何已启动的试点会话先关闭本机入口与代理流量，再回收 SSH 进程。撤销状态不可读取或过旧时，保持关闭，不能靠已有本地记录续期。 |

OpenSSH 的 `GatewayPorts=yes` 可能把显式 `127.0.0.1` 请求变成通配监听。创建后的端口检查只能发现问题并关闭已创建的监听。
主机密钥相同也不能证明服务配置仍未变化。试点应由维护者保证批准的服务端实例在当前许可有效时不修改有效策略。
**部署验收必须验证变更顺序。** 维护变更前停止签发并撤销现有许可，确认所有旧会话已关闭、转发已释放后，才允许改变服务端配置或重启实例。
仅有签名许可、到期记录或主机密钥未变化均不能替代关闭证据。变更后重新审查有效策略，再签发新许可。
无法落实此要求的部署拒绝启动真实试点。本轮没有登记任何真实目标。

## 4. 启动配置冻结与参数

从已审查的直接目标字段生成最小 SSH 配置。进程通过 `-F` 指向这份配置；用户和系统 SSH 配置不参加解析。
禁止从任意用户配置原样复制选项，也不能把整份 `ssh -G` 输出当作可安全重放的启动配置。
任意配置里的 `Match exec` 本身可能执行命令；只对没有 `Include`、执行钩子或动态展开的内建配置做结构校验与离线 `ssh -G`。
冻结快照同时关联原 `BoundTarget` 指纹、实际连接目标、主机信任及撤销输入、会话代次和本机代理修订。
握手预检、转发启动和监听复核都使用这份快照，区别限于是否启用显式转发或执行固定探针。
[OpenSSH -F](https://man.openbsd.org/ssh#F) · [SSH 配置解析与 Match](https://man.openbsd.org/ssh_config#Match)

配置、只读公钥文件与必要的撤销资料放在当前用户独享的本机目录。预计用平台 API 确认文件和父目录无重解析与越界，
采用拒绝写入或删除共享的句柄保留到最后一个依赖进程结束。现有信任或撤销变化使整个快照失效，
不能继续依赖过期内容。复核 Windows OpenSSH 能在这些共享条件下读取同一对象，无法证明时拒绝。
[Windows 文件共享与句柄](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)

| 类别 | 拟议约束 |
| --- | --- |
| 进程与端点 | 只使用既有系统 OpenSSH 路径和独立参数，目的地为已冻结端点。非交互转发用 `-N -T`、`ExitOnForwardFailure=yes`、`ConnectTimeout=8`、`ConnectionAttempts=1`、`ServerAliveInterval=5`、`ServerAliveCountMax=2`。不复用现有 SSH 会话，不后台分叉；交互认证在预检阶段完成，启动时复用绑定凭据或本机 Agent。 |
| 信任选项 | 启用 `StrictHostKeyChecking=yes`，仅用冻结的专用 `UserKnownHostsFile`，在保留适用的全局信任限制及撤销约束后才可设置 `GlobalKnownHostsFile=none`。明确算法和撤销来源，禁用主机密钥自动更新、DNS 替代信任及自动添加 Agent。若既有信任约束无法保留便拒绝。 |
| 转发约束 | 仅附加 `forward_args` 返回的一条固定回环转发。冻结文件中不带任何本地、远端、动态或 stdio 转发。探针启用 `ClearAllForwardings=yes`。实际转发使用无既存规则的冻结配置和 `ClearAllForwardings=no`，否则显式转发也会被清掉。禁止跳板、外部主机核验命令、Agent/X11 转发和 TUN。冻结配置不带远端命令、本机执行钩子或任意环境转发，探针只使用固定远端命令。 |
| 进程归属 | 保持既有 Job Object 回收语义。对新转发入口使用在进程开始执行前就将其加入 Job 的机制，例如 Windows 的进程创建 Job 列表。若无法建立受控进程归属，拒绝启动；探针、SSH 子进程和本机入口一起归属同一会话。 |

## 5. 实际监听与本机回执流程

1. **启动前复核。** 核对有效策略和撤销状态、已验证的主机身份、平台、账号、原配置指纹、冻结资料和进程所有权、本机代理可用性与修订号、代次，以及批准端口。先用只读远端检查排除占用。应用创建并持有独占的本机 `127.0.0.1` 入口，端口不可重绑，也不可与上游重合。Windows 可在 bind 前使用 `SO_EXCLUSIVEADDRUSE`。入口此时只具备验证能力，不创建通用 Relay。
2. **启动受控 SSH 后检查监听。** 单独用相同冻结信任运行只读探针，采集目标数值端口的全部 IPv4/IPv6 监听地址。建议基于 `.NET IPGlobalProperties.GetActiveTcpListeners()`，仅送回该端口的地址和会话回执。初版要求存在精确 `127.0.0.1`，且该端口地址集合只能证明这一个监听范围。通配 `0.0.0.0`、`::`、非回环、意外 `::1` 或 IPv4 映射 IPv6、监听缺失、查询不完整或歧义均关闭本次转发。进程存活和地址快照都不足以证明监听归属。
3. **验证转发归属。** 本机用系统随机源生成单次 128 位随机值，绑定当前代次、本机入口、SSH 子进程与远端端口。由已验证探针的受限 stdin 将一帧定长数据交给固定程序，发送后关闭输入。随机值不进入命令行、日志或前端状态。程序只连接目标的 `127.0.0.1:<已批准端口>`，发送定长回执后关闭写端。本机必须在同一入口上收到唯一的完整匹配帧和 EOF，在有限窗口里验证并消费随机值。缺失、错误、重复、截断、额外字节、过期及并发竞争均拒绝或关闭相应连接，已消费的验证连接全部结束。探针 stdout 上的回声不能代替转发路径上的实际接收。
4. **开放数据。** 单次回执、监听、进程归属和最后一次目标及策略复核必须同代次成立。此前本机入口不得向已有代理或 Relay 连接，不转发任何 HTTP、SOCKS 或普通 TCP 字节，也不保留待转交的验证客户端数据。通过后才启动现有 General Relay，将入口原子切换为仅接入该 Relay。连通性检查单独记录；这一步确认路径归属及安全边界，不能宣称公网出口健康。
5. **持续约束。** 开放后对会话代次、活动代理、SSH 进程和许可期限持续监测。单调时钟到期后停止接入并回收现有连接，复核监听或撤销证据失败时也关闭。远端回环并非用户级隔离，试点仅用于维护者明确认可的可信、受管理目标。

[Windows 独占套接字](https://learn.microsoft.com/en-us/windows/win32/winsock/using-so-reuseaddr-and-so-exclusiveaddruse) · [IPv4/IPv6 监听 API](https://learn.microsoft.com/en-us/dotnet/api/system.net.networkinformation.ipglobalproperties.getactivetcplisteners?view=net-10.0)

## 6. 安全关闭和资源回收

| 触发条件 | 处理 |
| --- | --- |
| 建立或验证超时、取消、无法加入 Job | 使用有限的总建立预算与独立的读写时限，任一步失败即关闭入口。取消使代次先失效。回收探针、SSH、Job、管道与读线程，晚到回执无效。 |
| 端口冲突、权限拒绝、错误监听 | SSH 生存期检查与只读监听用于分类。只有明确端口冲突且政策仍有效，才允许按已批准范围另建计划；固定端口给出失败。主机拒绝、监听异常或错误原因不明时停止，不申请额外地址或权限。 |
| SSH 退出、断网、策略撤销或到期、目标或代理变化 | 原子停止接受及接入新数据，关闭所有验证与代理连接，调用现有 Relay 停用和 Drop。终止应用持有的 SSH 与 Job，释放本机端口，清理本次冻结资料。维护者可在原身份仍可信时只读查看远端监听释放；不可达则标记未确认。 |
| 用户重试 | 从新一轮策略、身份、冻结配置、代次与回执重新验证。仅当原条件仍满足才考虑原端口。禁止对旧代次重开入口，禁止结束远端第三方进程或清理远端配置。 |

在计划实现期要验证同一取消事件同时覆盖所有线程与 socket；关闭主进程后，辅助进程不能继续持有输出管道或让入口复活。
`ExitOnForwardFailure` 只覆盖建立转发失败，后续数据链路或权限变化由上述流程处理。
[OpenSSH ExitOnForwardFailure](https://man.openbsd.org/ssh_config#ExitOnForwardFailure)
