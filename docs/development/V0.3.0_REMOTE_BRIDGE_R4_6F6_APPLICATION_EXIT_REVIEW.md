# R4.6-F6 应用退出协调

本阶段基线为 `653a175f2fbb4f12ce14987bed99d5ddd56bd851`。原 V3 已确认，退出回调返回后可能先结束进程，清理线程仍持有未处理资源。[V3 原观察](V0.3.0_REMOTE_BRIDGE_R4_6_FINAL_ACCEPTANCE.md#v3-原生应用退出)

## 退出边界

- 正常退出请求先停收新桥接工作，事件循环继续运行。唯一协调器等待已接纳操作释放凭证，再由原清理线程退休 Store、释放传输、认证会话和缓存。正常完成后由 Tauri 继续退出。
- 总清理等待上限 3 秒，使用回执及条件变量。日志的停止回执另有最多 200 ms。重复请求复用已启动的协调，最终退出事件保留原 200 ms 兜底。Tauri 明确不可拦截的重启码仍走最终事件的兜底路径。
- 退出诊断为 `completed`、`timedOut` 或 `failed`。这些结果描述本机操作排空和资源处理。超期时保留最后确认的 Report 和 Tray，可能仍显示 Connected。被测 Job 及本机套接字由进程退出释放时，也不会因此记录应用清理完成。

| 场景 | Windows 原生进程夹具 | 真实 Tauri/Wry 事件循环夹具 |
| --- | --- | --- |
| 无争用及重复退出请求 | PASS，唯一完成回执，Report/Tray 均为 Disconnected | PASS |

| Store 争用在期限内解除 | PASS，释放锁后完成清理及发布 | PASS |

每个场景由外部观察进程等到测试应用真正退出，再验证两条自有 Windows 子进程句柄已终止、独占文件锁可重新获得、环回监听已关闭。F1–F3 既有六项分离用例在两种宿主各跑 18/18，F4/F5 候选场景也通过。超期夹具保留用于证明析构未完成的合成占有文件。

## Wry 加载器诊断

Windows 版本为 `10.0.26300.0`，已安装 WebView2 Runtime `149.0.4022.69`。旧隔离 EXE 的 PE 导入表要求 `comctl32!TaskDialogIndirect`。对该 EXE 的加载器跟踪观察到 WinSxS 实际加载 Common Controls `5.82.26100.8328`，该 DLL 的导出表缺少该入口，且测试在 WebView2 初始化前即以 `0xC0000139` 退出。

只在隔离构建中链接 Common Controls v6 manifest 后，加载跟踪实际观察到系统 WinSxS 的 `6.0.26100.9818`，测试进程可正常启动并运行真实 Wry 退出事件。项目构建、依赖、发布配置和系统文件保持原样。用例调用生产退出协调回调，夹具无需生产插件、窗口或真实用户配置。

复跑 `node scripts/fixtures/run-r4-6-final-acceptance.mjs --f6`，加 `--wry` 运行 Wry 宿主。加载跟踪及回执日志位于本机 `artifacts/v0.3.0/remote-bridge-r4-6/remediation/`。实际交互 PTY 与完整进程树、远端退出副作用和设备联合验收仍待验证。

首次全量发现共用 Cargo 输出会把夹具 manifest 带入正式二进制链接，触发重复资源错误。原生和 Wry 夹具现使用各自的隔离 Cargo 目录，两套候选复验通过。正式构建重新生成了自身的构建脚本产物。
