# 目标服务连通性检查：轻量优化建议

状态：方案，尚未实现目标自定义及对照检测；2026-10-22 按维护者反馈收窄范围。本文件替代此前以大量应用适配为核心的建议。

## 已完成的界面调整

概述在当前代理地址上方、切换代理前显示连通性结果，后续依次展示网络观测、环境变量和应用入口。系统代理和 TUN 始终直接展示，不折叠。应用搜索框位于刷新按钮前。

## 产品方向

核心问题是“当前代理能否访问这个服务”，无需为大量应用编写适配器。建议将新增投入集中于通用的目标服务检查；既有应用启动和配置功能暂保留，不继续扩大应用规则维护范围。

最小流程：选择常用服务名称 → 点击检测 → 查看当前代理路径的结果。检测地址由 RouteSpan 维护，自定义地址仅放高级选项。可选启用“不使用应用层代理”的对照请求，帮助判断代理是否改善了访问。

已有 `connectivity.rs` 会显式经过当前 HTTP/SOCKS 代理请求固定的 Google、GitHub、Cloudflare 目标；可复用其超时、协议探测、错误展示与 revision 校验基础，扩展目标输入和可选对照，不需要重建整套检测。

## 为什么不用 ping 作为主要结论

Windows ping 使用 ICMP 检查 IP 层可达性，不验证 HTTPS 服务，也不是经过 HTTP/SOCKS 代理的请求。目标禁用 ICMP 时 ping 可能失败，但 HTTPS 仍正常。

如果用户说的“ping”泛指发请求做健康检查，这个方向可行；实际实现使用显式代理的 HTTPS 请求，界面称“检测连接”。

## 最小结果展示

| 当前代理请求 | 对照请求 | 可以给出的结论 |
| --- | --- | --- |
| 成功 | 失败 | 当前代理路径可达，对照路径失败 |
| 成功 | 成功 | 两种路径均可达，展示各自响应时间 |
| 失败 | 成功 | 当前代理路径检测失败，可检查代理或分流规则 |
| 失败 | 失败 | 本次均未成功，分别展示错误，不直接归因为代理故障 |

未开启对照时，只显示代理路径结果，不推断代理是否必要。

响应时间是本次请求耗时，不称为带宽、网速或 ICMP 延迟。HTTP 401/403/429/5xx 应展示响应状态：收到响应与业务健康是两件事，不能一概报网络不通，也不能一概标服务健康。

## 必须保留的结论边界

- 成功表示 RouteSpan 通过选定本地代理完成了目标请求，不能证明另一个运行中应用也使用了该代理。
- 本地代理可能按自身规则直连该目标；请求经过本地代理不等于一定经过远端节点。
- 对照请求应关闭 HTTP/SOCKS 自动代理与环境变量继承；但系统 TUN/VPN 仍可能接管流量，因此标为“不使用应用层代理”，不能承诺物理直连。
- 不需要账号、API Key，也不发送应用业务数据。普通页面响应只作可达性证据；真正的服务健康结论应由该目标明确的健康接口约定支持。

## 最小实现范围

1. 常用服务列表，显示当前活动代理；点击后发起请求；自定义地址放高级选项。
2. 可选对照检测；结果按路径显示 HTTP 状态、耗时、错误和检测时间。
3. HTTPS 地址校验、明确超时、无副作用请求、不携带凭证、限制重定向；切换代理后旧结果作废。
4. 单独覆盖握手失败、TLS 失败、超时、服务返回错误及代理切换竞态。

不新增应用规则库、自动修改应用配置或进程流量监控。先把一个目标的代理路径检测做准确。
