# Authenticated local relay — M8 design

**Status: implemented in `v0.2.0dev`; shared-host acceptance remains pending.** Both reverse-forward routes now terminate at backend-owned authenticated relays. Loopback binding alone is still not considered user isolation, and release claims remain gated on the real different-UID checks listed below.

## Threat model and invariant

The remote consumer's request must prove possession of an unpredictable bridge-session credential before the relay connects to a fixed allowlisted upstream. A different UID without that credential is rejected; the same UID shares a trust domain, and root is outside user-space isolation guarantees. A port number, loopback binding, remote PID or provider key is not authentication.

## Required lifecycle

1. Generate a fresh ≥256-bit CSPRNG token for **each** bridge session. Keep the active value in backend-owned, zeroized memory; no `Debug`, serialization or frontend getter. A reconnect creates a different value even when reusing the same remote port.
2. **General Proxy:** replace the current direct `ssh -R remote:local-client` with `ssh -R remote:local-authenticated-proxy-relay`. The relay must select HTTP versus SOCKS5 from the validated Active Proxy protocol, enforce proxy authentication before connecting to the fixed local upstream, and remove its own credential before forwarding. HTTP CONNECT and SOCKS5 username/password need separate tests; Mixed must not accidentally admit a no-auth protocol path. The backend may furnish credentials only to a managed remote session environment, never to WebView-visible `Summary.environment`, copied export text, error messages or command arguments. This depends on the session-environment work; do not leave the old direct forward as a fallback.
3. **AI Route:** authenticate a distinct header at the local relay before forwarding an otherwise unchanged request to the fixed CC Switch upstream. Codex supports provider `http_headers`; Claude Code documents `ANTHROPIC_CUSTOM_HEADERS` only from **v2.1.227**, so older supported 2.x versions must be treated as incompatible with this delivery path, not given unauthenticated access. Review and test the actual CLI and VS Code Remote consumers before storing a transient session header in the existing owner-protected remote user configuration. This is a bridge credential, **not** `Authorization`, a Provider API key, `auth.json` or the existing public `PROXY_MANAGED` placeholder. Strip it before forwarding. Existing configuration transactions must restore it conflict-safely and rotate it when the bridge reconnects without copying it into backups that outlive the session.
4. Establish credential delivery and the authenticated local listeners **before** advertising the remote forwards as connected. Reject missing, wrong, expired or cross-session tokens. If injection, remote readback or either route's verification fails, tear down the new forwards and listeners; do not switch back to the present unauthenticated route. Disconnect, target switch, process failure and shutdown revoke immediately. Already-open connections need an explicit shutdown policy, not only an accept-loop stop.
5. Keep token values out of IPC summaries, frontend state, logs, diagnostic reports, URLs, process command lines and SSH history. Use fixed status/error categories. Test byte-accurate passthrough only after authentication, including streaming, tool calls, `CONNECT`, SOCKS5 and upstream errors. Do not reinterpret model or response semantics.

The current VS Code user `http.proxy` clue is not proof that an extension host can send proxy credentials. VS Code documents `http.proxyAuthorization` as limited to specific legacy networking scenarios and does not support SOCKS5 proxy authentication in its Chromium layer. A consumer that cannot authenticate must be shown as unavailable, not silently routed through an unauthenticated listener. See the [VS Code network documentation](https://code.visualstudio.com/docs/setup/network), [Codex provider-header reference](https://developers.openai.com/codex/config-reference), [Claude environment-variable reference](https://code.claude.com/docs/en/env-vars), and [OpenSSH remote forwarding semantics](https://man.openbsd.org/ssh.1).

## Current implementation

- General proxy forwarding terminates at a loopback-only relay. HTTP uses Basic proxy authentication and SOCKS5 uses RFC 1929 username/password authentication; the relay strips its credential before connecting to the fixed Active Proxy endpoint.
- AI forwarding uses `X-ProxyEnv-Session`. Codex receives it through provider `http_headers`; Claude receives it through `ANTHROPIC_CUSTOM_HEADERS`. Claude versions older than `2.1.227` fail closed.
- Every relay owns an independent 256-bit random token and a non-secret random session id. Tokens are compared in constant time and retained in zeroizing backend buffers where practical.
- Managed proxy terminals source `~/.proxyenv/sessions/<session-id>/env.sh`. The file is created through SSH stdin with mode `0600`; its token is not placed in the SSH command line or WebView summary. The visible manual-export block is suppressed for authenticated sessions.
- Reconnect rotates tokens. Existing ProxyEnv-owned Codex or Claude projections are updated through their established preview/apply transaction without a second user decision. Unowned configurations are not modified.
- Disconnect revokes both local capabilities before best-effort removal of the remote session environment. Relay drop also shuts down tracked active streams.
- The previous unauthenticated Codex relay remains test-only for regression coverage; production forwarding cannot fall back to it.

## Release tests

Different UID without token rejected for **both** forwarded ports; same session's authorized consumer succeeds; wrong and old tokens rejected; disconnect revokes immediately including active streams; reconnect rotates; missing remote credential fails closed; failure paths never log or render token; fixed upstream cannot be replaced by frontend input; concurrent sessions cannot cross-authenticate. Exercise real shared-host loopback behavior and CLI/extension/proxy clients, not only mocks. The existing transparent Codex streaming/tool tests must continue to pass after authentication.
