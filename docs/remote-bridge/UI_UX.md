# Remote Bridge UI/UX — Simple and Advanced

The connected page explains AI-only, proxy-only and combined use. Action availability follows the required capability: AI verification follows AI health; proxy testing/managed terminal follows General Proxy health; Skills follows the live SSH session. An unrelated unavailable route must not disable healthy actions.

Setup uses a fixed two-column workspace: choose an SSH connection on the left, then configure its capabilities on the right. The list shows at most five complete rows before scrolling internally; its scrollbar stays faint until hovered. Each row identifies its OpenSSH, VS Code Remote, MobaXterm or ProxyEnv source and authentication method. Outside clicks and Escape dismiss the action menu. Blank list space can clear the selection. Edit and add share one dialog; removing imported connections only hides them in ProxyEnv. Cancel and Establish bridge remain inside the current-connection panel, with the workspace border fully visible.

With no SSH connection selected, the existing instruction remains above decorative pixel mascots adapted from the user-supplied `proxyenv-pixel-mascots-v2` SVG/CSS assets and design board. Muted orange Claude and soft blue Codex have theme-aware palettes, with idle, coding, sleeping, music, coffee, reading, gardening and gaming actions. A finite action completes before a short fade switches to another random scene; every third scene pairs the characters for working, resting, gardening, gaming or music. Polling does not reroll the scene. The stage has a fixed size so switching cannot shift the page. These are illustrative mascots, not official brand logos or connection-result indicators. Reusable Vue/SVG sprites add no runtime dependency, network request or animation timer. Animation pauses when the remote page/document is hidden or the stage scrolls out of view, stops when selection removes it, and becomes static for reduced-motion users. It does not affect SSH selection, authentication or bridge operations.

The app shell fills the actual window rather than staying capped at the original 880px width. The header and any global warning reserve their own height; the page uses the remaining content area, not a viewport height minus a hard-coded header. Content has a 1360px maximum reading/workspace width on large displays. Above 760 CSS pixels setup keeps two columns; narrower windows stack the panels and reserve space for at least two complete SSH connections when present, including the list heading and row gap. Five complete SSH rows fit the normal desktop layout; short/narrow windows show fewer rows with internal scrolling instead of compressing their text. Current-connection content can scroll independently at constrained heights, while Cancel/Establish remain outside that scroller. Connected Overview/Advanced, local environment and settings scroll in the content area without moving the title bar. Authentication terminal content does not flex-shrink out of sight; constrained dialogs scroll internally.

`scripts/test-remote-layout.mjs` is an optional Playwright geometry regression using the existing development review previews, not a real SSH target. Run a dev server, supply Playwright through the normal package lookup or `PROXYENV_LAYOUT_PLAYWRIGHT` (absolute package entry), and optionally supply `PROXYENV_LAYOUT_BROWSER` (installed Chromium executable). `PROXYENV_LAYOUT_URL` defaults to localhost:1420; `--screenshots` writes ignored previews under `.debug-tmp/remote-layout`. It tests default/maximized/compact viewport transitions, light/dark, empty selection, add dialog, retained authentication states, connected views, local environment and settings. CSS viewport simulation does not substitute for real Windows 125%/150% display-scaling acceptance.

Bridge local network reuses the active proxy from Local environment. Local listener availability is separate from remote bridge connectivity. CC Switch AI routing requires a loopback listener owned by CC Switch and a bounded successful local `/health` response; an unidentified listener does not enable the switch. Detection confirms the shared local service, not individual Claude/Codex route toggles. Its detected URL appears beside the state. A short reminder asks users to enable the routes they need; no per-agent success badge or requirement to enable both routes is introduced. Discovery follows changed CC Switch ports, with no system proxy, redirects, credentials, AI requests or SSH probes. Loss of the route disables and clears the setup switch; its return makes the switch available without overriding the user's choice. Established tunnels keep their original endpoint and require reconnection after a route-port change. Both capability choices have equal height. The shared question-mark tooltip explains CC Switch → Settings → Routing → Local routing → Master routing switch → enable Claude/Codex routing. Setup omits the redundant subtitle, capability description and technical prerequisites. The backend still performs SSH validation and port allocation before forwarding.

CC Switch discovery starts when the app mounts, independently of SSH summary loading and before the remote page is opened. One application-owned cache and non-overlapping two-second polling provide the latest state and URL to setup, even while another page is visible. Entering setup consumes that cache in its first render, without a duplicate discovery. Refreshes retain the previous observation until the result arrives; unchanged observations do not replace the cached object, and a changed port is applied without an intermediate not-detected state. An unfinished first check is shown as checking, not missing. CC Switch AI routing defaults to enabled when detection confirms availability. A manual off choice is retained for the current page session. Temporary unavailability disables the effective switch without discarding that choice; recovery restores the preferred state instead of forcing routing on or leaving the default off. Background discovery never retargets an established bridge.

The shared Add/Edit SSH dialog keeps destination examples, authentication explanations, identity-path guidance and edit/copy explanations in the existing question-mark HelpTooltip instead of persistent paragraphs. Field-validation errors stay inline and associated with their input. The tooltip mounts inside its nearest open native dialog when present, keeping help visible and keyboard-accessible in the modal top layer; ordinary page tooltips still mount in the document body.

The compact identity authentication row reserves its single-line path area; Browse appears only when identity mode is selected, with a 30px action height inside a stable 36px row. Long paths are ellipsized with the full path available on hover. The native file picker accepts extensionless names; Rust validates path safety, readable regular-file metadata, size and a bounded OpenSSH/PEM header before returning only the normalized path. Cancel retains the previous selection. Saving revalidates the same file, and OpenSSH still owns actual key decoding, unlocking and server authentication.

All SSH form fields use the shared FieldValidation / HelpTooltip treatment: a red input border and a label-side error icon, with correction text available on hover or keyboard focus and linked to the field for screen readers. No below-field error rows expand the dialog. Invalid submit focuses the first invalid field. Names are limited to 32 Unicode characters in both frontend and backend, with a visible count. Save errors remain inside the open dialog, preserve input and clear on editing; a missing backend command explicitly requests a rebuild/restart rather than suggesting incorrect SSH or proxy settings.

Initial connection retains the setup layout through checking, SSH authentication and bridge construction. The original establish action stays visible, disabled and labeled Establishing bridge with a small inline spinner; no detached Processing status appears below the panels. The content-sized OpenSSH dialog is at most 440px wide with a 40px response field. Its submit action remains mounted during bridge construction and shows the same disabled loading treatment. Reduced-motion preferences keep textual feedback without rotation. Existing secret clearing and fixed-length password masking are preserved.

Authentication rejection and other errors appear in a reserved inline area beneath the response field, not as a floating notice. Error visibility does not move the field or resize the centered dialog; long messages scroll inside that area. The field references the error for accessibility. Dialog text is selectable, and Copy prompt reuses the shared modal-safe clipboard helper to copy the displayed OpenSSH prompt and localized error only—never the password, verification response or its mask. Copy success/failure feedback stays in the same button and does not change bridge state.

Selectable text includes the dialog title, status label, field label, fingerprint and diagnostic values, not only terminal output. Authentication focus watches individual prompt/status values rather than newly allocated polling snapshots, so an unchanged poll cannot refocus the password field and interrupt selection or Ctrl+C. New challenges retain the existing input-focus behavior without scrolling the dialog.

After the bridge is connected, the default next actions use the managed terminal, Open in VS Code, or—when MobaXterm is installed—Open in MobaXterm. MobaXterm is not launched from target selection. A selected first-level Moba bookmark opens that bookmark; another compatible SSH target opens the MobaXterm application so the user can continue with the same saved connection details. MobaXterm is a connected-target capability, not a General Proxy advanced action. A hint beside Open in VS Code explains that ProxyEnv temporarily isolates the remote account's VS Code Server from inherited proxy settings, keeps loopback AI routes direct, preserves local settings, and may require reloading an existing remote window. No third-party extension binary or user startup file is changed.

General Proxy has no username/password UI or fallback. Advanced retains only the token-free terminal setup command and technical diagnostics. The AI Route's session header is never displayed or copied. Successful copying does not claim that a running extension host has received new environment variables.

**Status: implemented on `v0.2.0dev`; real-device release acceptance remains pending.** The continuous setup/status page and shared warm ProxyEnv design remain the foundation. See `DESIGN.md` for tokens and accessibility rules.

## Simple (default)

The remote page mounts hidden at application startup and preloads its local SSH connection list. Local proxy and CC Switch observations initialize capability controls even if detection finishes after mounting. Opening the tab reveals the same page and list instance with `v-show`, rather than mounting an empty view and loading it on first navigation. Preloading does not connect SSH, start a bridge or enable AI tool access; an explicit capability choice is preserved across subsequent observations and page switches.

The connected page defaults to Overview, following the October connected-overview design. Its four groups are the bridge header, two equal capability cards, AI tools and Skills, and a bottom launch bar. The header shows one target and overall connection status, the SSH address/source/cleaned configuration path, and an independent server-direct observation. A failed server-direct check uses a yellow warning, not the bridge failure state. Overview/Advanced, Recheck and Disconnect remain together in the top toolbar.

Capability cards show the session's original local endpoint → remote loopback port, not the internal Relay's transient port. They do not substitute a newly selected local proxy into an existing bridge. Network proxy and AI routing retain separate health states and can be independently paused or resumed after connecting. Switches wait for backend confirmation and block repeated actions during setup/configuration. A paused relay closes its active connections and refuses new traffic while reserving the same forwarding port; the other relay and SSH transport remain intact. Recovery preserves paused gates. First-time activation adds only the requested forward, using existing SSH authentication and loopback verification rather than restarting the healthy lane. General Proxy pause removes its managed shell environment and updates/restores owned VS Code network settings. AI pause first restores the enabled tools through their existing hash-checked backup transactions; resume reapplies those tools with the current local profile. Multiple files remain separate transactions: a partial restore is explicitly reported with accurate tool states, never described as full success or overwritten on conflict. Existing processes need restarting after configuration changes. Codex and Claude Code access switches continue using the existing tool adapters.

The capability labels, addresses and client names share the SSH metadata's plain 11px typography. Local and remote labels share the first row and addresses share the second row, connected by a plain muted arrow aligned with the addresses. Client and protocol details sit separately below the local address. Both cards use the same column proportions and row spacing. Long content wraps within its column rather than needing horizontal scrolling or expanding the page. The header's Server direct network observation has a small globe icon and concise Available/Unavailable badges; unknown, checking and not-yet-checked remain distinct. An unavailable direct connection uses a warning treatment and does not imply bridge failure.

AI tools appear side by side, with bundled OpenAI/Claude identifying marks and one compact configuration state per tool. Configuration does not imply successful AI requests; Codex synchronization is not inferred from Claude's profile state. Skills appear as merged-name rows with separate read-only agent status chips. The count includes enabled agent projections, not unique names or disabled copies. Manage reveals and focuses the existing Advanced Skills controls without adding another backend or polling loop. Terminal, VS Code and MobaXterm remain visible in that order; unavailable clients are disabled with explanatory help instead of disappearing. MobaXterm help explains the existing manual terminal-environment handoff, not automatic injection. Capability and tool grids stack at narrow widths; long names wrap and Skills can scroll within their list. Conflicts and failed operations remain visible with a safe next action.

Show useful public local/remote listening addresses in Overview, but hide `ssh -R`, `NO_PROXY`, profile/catalog hashes, provider IDs, ownership markers, internal Relay ports and session tokens. Never put a token in Advanced either. Authentication prompts use a compact content-sized dialog. The terminal, response field and action area are mounted before the first OpenSSH prompt arrives, then keep a stable position throughout authentication and core bridge construction. Prompt text is selectable. Password submission immediately clears the real secret and temporarily disables the field, while a fixed-length bullet mask preserves the visual entered state without retaining or revealing password length. A new prompt clears that mask and re-enables the field. The only changing authentication copy appears in the top-right status position: waiting for server, waiting for input, or verifying. Successful SSH authentication immediately continues into core bridge construction without replacing the terminal or returning the user to a separate confirmation page. Overview opens when the verified core bridge is ready, while optional post-connect jobs update independently. Only the changing inner status receives a short opacity/vertical transition, and reduced-motion preference collapses it. No redundant step rail or repeated connection title.

## Silent transport recovery

After an established bridge loses SSH transport, the backend attempts recovery without reopening the setup flow. It reuses the selected target, ports, live relays and bridge-scoped SSH session credentials. A small in-page reconnecting status is sufficient: temporary outages, retries and successful recovery produce no popup or sound. Recovery starts by rebuilding the retained tunnel directly and uses a bounded 1, 2, 4, 8, 15 and 30 second backoff instead of waiting several minutes behind a separate SSH probe. Interrupted application requests are not replayed; the user may need to retry the affected message after recovery.

Authentication failure, a changed host/configuration or a changed active proxy pauses recovery. The page keeps the reason and retry action beside the connection status; it does not create a second lower-right in-app card. Manual retry resumes the retained target, ports, relays and session instead of rebuilding setup input. No password prompt opens automatically. Native reconnect notifications and their settings remain dormant in `v0.2.0dev`; recovery is silent unless inline user action is required. SSH login authentication remains independent from the removed General Proxy username/password feature. Manual disconnect, target replacement and app exit cancel pending recovery; recovery must never recreate a user-disconnected bridge.

## Advanced

The Advanced switch reveals effective SSH source, General Proxy and AI Route diagnostics, remote consumer vs local upstream port, runtime proxy match, token-free environment exports, bridge testing, Skills controls and diagnostic-only SSH configuration actions. Open SSH configuration, reveal configuration and VS Code settings actions are intentionally absent from setup and Overview. Protected tool dialogs continue to own tool versions, extension runtime, profile/catalog state and restore diagnostics. Display the provenance and limits of each observation; independent checks update independently. Advanced inspection does not silently enable routes or write files.

Overview/Advanced uses in-place visibility changes, so toggling does not remount tool controls, Skills state or operation feedback. The segmented control exposes pressed state and keyboard focus, follows reduced-motion behavior, and ships equivalent Chinese, English, Japanese and Korean copy. Desktop and narrow review previews are covered by the development harness; dark-theme and real-device behavior remain part of release acceptance.

The optional browser regression `node scripts/test-bridge-capabilities-ui.mjs` uses the same `PROXYENV_LAYOUT_PLAYWRIGHT`, `PROXYENV_LAYOUT_BROWSER` and `PROXYENV_LAYOUT_URL` settings as the layout harness. Synthetic IPC verifies independent on/off controls, non-optimistic state, disabled repeated clicks, and failure recovery without opening SSH connections or writing configuration. Real acceptance must additionally cover both lane pause/resume orders, an initially unselected lane, configuration conflicts and network recovery. After both lanes are paused, resuming reapplies VS Code network setup only when this bridge previously managed it. Already running tools/remote windows may require restarting/reloading to consume restored configuration.

Overview help opts into the shared tooltip's pin behavior: hover/focus previews it, click or Enter/Space pins it, and outside pointer input or Escape dismisses it. Other existing help remains hover/focus-only by default. Pinned help is selectable and stays within the window bounds. For a focused layout regression, set `PROXYENV_LAYOUT_ROUTES=remote-connected,remote-connected-advanced`; omitted filters retain the full existing route matrix. The connected checks cover two-column/stacked cards, persistent disabled launch entries, bottom launch visibility, pinned-help dismissal and focus transfer into the existing Skills manager.
